# Admin Feature Reuse Matrix — Airbone → StreetPlayR Unified Admin

> Analysis only. No code modified. Compares Airbone's reference architecture against what **already exists** in StreetPlayR (`app/admin` "OpsOS") and NECTAR (`apps/ecosystem-ops` "OpsOS"). Those two are near-duplicate scaffolds of the same custom admin — the unified admin is effectively consolidating them, using Airbone as the maturity benchmark.
>
> **Priority key** — P0 = essential, P1 = important, P2 = nice-to-have.

## Summary read

- **P0 gaps** (do first): generic DataTable w/ pagination, RHF+zod forms, Dialog/ConfirmDialog reuse, shared toast system, background-job runner for webhook/notification reliability.
- **P1 gaps**: ABAC row-level permissions, CMS version/rollback, media library, layered API convention + error taxonomy, audit trail, real charting library.
- **P2 / polish**: nav role-gating, shared ErrorState, notification inbox, settings-as-JSON pattern, design-token consolidation, StatusBadge consolidation.
- **Do not import**: Airbone's NextAuth stack, its aviation/education domain models, or its literal branding/design tokens.
- **Consolidation note**: StreetPlayR's `app/admin` and NECTAR's `apps/ecosystem-ops` are near-identical parallel builds of the same OpsOS concept (same nav sections, same Zustand platform-store pattern, same command palette). The unified admin should pick **one** of these two as the base (StreetPlayR's is slightly more feature-complete — has a working CMS and stronger server-side RBAC) and port NECTAR's ops routes/queries into it, rather than building a third parallel implementation informed only by Airbone.
